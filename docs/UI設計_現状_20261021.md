# OntoMap 画面設計（現状）— 改善案の検討用

作成日: 2026-10-21。対象は Mac アプリ「OntoMap」の画面（中身は Web 画面。FastAPI ＋ 素の JavaScript・SVG）。
コード: ontomap/app/web/index.html（148 行）、app.js（994 行）、style.css（200 行）。

## 0. 依頼文（GPT に貼るとき用）

以下は、特許文書の「俯瞰マップ」アプリの画面設計の現状です。利用者は特許調査・技術企画の担当者で、
数百〜数千件の特許を地図にして、技術のまとまり・出願人の位置・用途をまたぐ似た技術を探します。
次の観点で、改善案を優先度つきで出してください。各案には「何が問題か」「どう変えるか」「期待する効果」「実装の重さ（小・中・大）」を書いてください。

1. 初めて使う人が迷わないか（用語・手順・画面の数）
2. 地図の画面の情報量と配置（左右の欄、地図の見やすさ、操作）
3. 「なぜ近いか」の説明の分かりやすさと信頼感
4. 辞書（オントロジー）をつくる・育てる流れの分かりやすさと手間
5. 一貫性（用語・ボタン・ステップ・色・状態の表示）
6. 見落としているエラー・空の状態・待ち時間の扱い

制約: Mac アプリ（デスクトップ、横 1280〜1920px）。日本語の画面。外部サービスへの送信なし（AI はアプリに組み込まず、利用者が自分でチャットに貼る運用）。

## 1. 何をするアプリか

- 特許の一覧（CSV・Excel）を取り込むと、文書の近さで 2 次元の地図（点＝特許 1 件、等高線＝密度、見出し＝まとまりの名前）を描く。
- 近さの測り方は 3 つから切り替える。
  - 文埋め込み: 文章の意味の近さ（学習済みの日本語文埋め込みモデル）
  - 関係: 課題・解決手段・用途の語を辞書で拾い、「手段→課題を解決する」「手段→用途に使われる」などの関係の一致で測る
  - ハイブリッド: 上の 2 つを半分ずつ
- 関係の近さに使う辞書（オントロジー）は 2 層。
  - 共通層: 分野で共有する辞書。同梱のもの（無機材料・MOF・技術（試作）＝上層＋無機材料・電池・半導体の部品）か、利用者が作ったもの
  - 拡張層: マップごとの追加分（マップの文書で拾えない語を候補から採用）
- 共通層は「部品（分野）」に分かれることがある。文書の IPC・FI を見て使う部品を切り替える（例: 半導体の文書では「容量」を放電容量として拾わない）。

## 3. 画面ごとの設計

### 3.1 マップの一覧（#/）
- 見出し「特許俯瞰マップ」＋説明文＋「新しいマップを作る」ボタン。
- カード（幅 300px 以上の格子）: 名前、件数・作成日・元のファイル名、状態の札（完成／計算中 nn%／失敗）、ボタン（開く／計算し直す（失敗時）／削除）。
- 計算中のカードがあると 3 秒ごとに一覧を読み直す。
- 空のとき: 「まだマップがありません。…」の文。

### 3.2 マップをつくる（#/new）— 3 ステップ
1. ファイルを選ぶ: 点線の枠（置く／押して選ぶ）。CSV・TSV・Excel。
2. 列を対応づける:
   - マップの名前
   - 列の対応（2 列の格子。各項目に選択欄。必須は「名称」）: 名称・要約・課題・解決手段・用途・出願人・出願日・IPC・FI・公報番号・請求項 1・明細書（全文）。列名から自動で推測。
   - オントロジー（共通層）の選択欄と「YAML を追加」
   - 先頭 5 行の表
   - 「やめる」「地図を作る」
3. 計算する: 進み具合の棒と、段階の文（「文章の意味の近さを計算しています」など）。2 秒ごとに状態を見て、完了したら地図へ。
- 明細書の列を選ぶと、用途の段落と用途の文を全文から切り出す（画面には出さない処理）。

### 3.3 地図（#/map/<id>）— 3 段組（左 300px・地図・右 400px）
ヘッダ: パンくずに「名前 · 件数 · 用途の判定元 · オントロジーの版」、右上に「オントロジーを育てる」「マップの一覧」。

左の欄（上から）
1. 近さの測り方: 3 つの切り替え（文埋め込み／関係／ハイブリッド）と説明文。配置が島に分かれたときは「島どうしの距離には意味がありません」を添える。
2. 検索と絞り込み: 語（名称・要約・出願人・分類）、出願年の範囲、IPC の前方一致、用途の選択、出願人（入力補完）、該当件数、「条件を消す」。
3. 色分け: なし／用途／出願人／分野の部品（部品のある共通層だけ）。下に札（最大 3 つ選べる。件数付き）。
4. 表示: 等高線、まとまりの見出し、用途をまたぐ「課題と解決手段が近い」組（線で結ぶ）、色分けした群の範囲と年の動き（等高線の範囲と、出願年に沿った重心の軌跡）。
5. 該当する文書の一覧（絞り込みの結果）。

地図（SVG）
- 点（文書）、等高線（密度）、まとまりの見出し（2 行の語）、選んだ文書と近い文書を結ぶ線。
- 操作: ホイールで拡大縮小、ドラッグで移動、右上に「＋」「−」「全体」。点に重ねると吹き出し（名称など）。点を押すと選択。
- 測り方を切り替えると、点が 0.9 秒で動いて移る（同じ文書の位置の変化が見える）。
- 左下に凡例（色分け・等高線）。

右の欄
- 何も選んでいないとき: 「用途をまたぐ『課題と解決手段が近い』組」の一覧（関係の近さが高いのに用途が重ならない組）。押すとその組を選ぶ。
- 文書を選んだとき:
  - 名称、書誌（公報番号・出願人・出願年・IPC・使った部品・用途）
  - 折りたたみ: 要約（開いた状態）・課題・解決手段・用途の文（近い理由の確認に使う）・用途の段落（地図の計算に使う）・取り出した関係（n 件）
  - タブ: 文で近い／関係で近い／合わせて近い（各 10 件。類似度と用途の札）
  - 近い文書を押すと「近い理由」の枠: 3 つの近さの値と順位、一致した関係の対（この文書の関係／相手の関係／一致度）
    - 印: 「用途の文で確認」（緑の枠）／「用途の文には無い」（点線の枠。用途の段落の周辺の語から拾った用途）
    - 切り替え: 「どの文書にも出る一般的な概念を含む関係を隠す」（既定で ON）、「用途が用途の文で確かめられない関係を隠す」
    - 注記: このマップで用途の文で確かめられる割合

### 3.4 オントロジーを育てる（マップ単位・#/onto/<id>）
- 冒頭の説明（2 層の考え方）。
- 3 つの箱（横並び）:
  - 2 つの層: 共通層の名前・版・概念数（部品があれば部品ごとの概念数と使った文書数の表）、拡張層（下書き）の件数、いまの地図の版、下書きが未反映の警告、共通層の新しい版の案内と「新しい版に切り替えて描き直す」
  - 概念が 1 つも拾えない文書の割合（段落ごと。共通層だけ／＋拡張層）と、拡張層の語が共通層の語を隠している箇所の警告
  - 地図を描き直す: 「共通層＋拡張層」「共通層だけ」の選択と「描き直す」。計算中は進み具合の棒。
- 候補の語: 段落のタブ（課題／解決手段／用途。件数付き）、表（語・文書数・使われ方の例・どう入れるか［選択欄: 新しい概念としてこの下に置く（提案・すべて）／既存の概念の別名にする（提案・すべて）］＋「入れる」「無視」）、「今の下書きで探し直す」。
- 拡張層に入れたもの（下書き）: 新しい概念／別名／無視した語の 3 箱。各行に「取り消す」。

### 3.5 共通層の一覧（#/common）
- 説明文（共通層・複製・版・発行・マップの版の固定）。右上に「共通層をつくる」。
- 自分の共通層のカード: 名前、元、作成日、「発行 vN」か「未発行」、「育てる」「削除」。
- 同梱の共通層から始める: 選択欄＋名前＋「複製して作る」。

### 3.6 共通層を育てる（#/common/<id>）— 5 つのタブ
見出しの下に「元・概念数・発行済み vN・下書きに未発行の変更あり・検査（直すところ n／問題なし）」。
1. 概要と発行: 部品の表（部品名・ID・振り分け［IPC・FI の前方一致を入力］・概念数・保存／削除）、部品を足す（ID・表示名・振り分け）、検査の結果（直すところ／注意）、変更点のメモと「vN として発行」、発行した版の一覧、変更の記録。
2. 概念: 部品の絞り込み・検索、概念を足す（部品・親・表示名・別名）、表（概念・別名・分野制限の札・親・部品・「直す」「削除」）。直すは標準の入力ダイアログ（prompt）2 回。
3. 格上げ候補: この共通層を使うマップの拡張層で採用された語。表（語・マップ数・採用したマップ・入れ方［新しい概念／別名、部品、置き場所］・「入れる」「無視」）。
4. 文書から足す: マップと部品を選ぶ→「探す」→ 候補の表（語・段落・文書数・例・入れ方・「入れる」）。
5. 別名の分野制限: 別名で概念を探す→ 使ってよい部品にチェック・理由→「この部品だけで使う」。一覧の表（別名・概念・部品・理由・「解除」）。

### 3.7 共通層をつくる（#/common-new）— 5 ステップ
1. 始め方: 3 枚のカード（チャットの AI に下書きを頼む（おすすめ）／CSV を自分で書く／既存の共通層を複製する）→「次へ」。
2. 下書きを頼む: 対象の分野（文章）、分野に分ける（分野名＋範囲、「分野を足す」）、概念の数（100/200/300）、見本の特許文（任意）→「プロンプトを作る」→ プロンプトの欄と「コピー」、使い方の説明。
3. CSV を取り込む: 雛形の CSV のダウンロード（自分で書く場合）、ファイル選択か貼り付け、名前→「取り込む」→ 結果（行数→概念数、層×型の件数、分野の振り分けの入力、検査、外したもの・まとめたものの一覧）。
4. 試し当て: マップを選んで「試す」→ 段落ごとの取りこぼし率（今の共通層／この下書き）、文書の振り分けの内訳、「拾えない語を足す」への案内。
5. 発行: 名前・メモ→「v1 として発行」→「この共通層でマップをつくる」「共通層を育てる」。

CSV の形式: 型,分野,中間概念,概念,別名（「|」区切り）。型は 課題／解決手段／用途。分野が空なら共通の層。「振り分け」行で分野の IPC・FI を書く。

## 5. 用語（画面に出る言葉）

| 用語 | 意味 |
|---|---|
| マップ | 取り込んだ特許一覧 1 つと、その地図 |
| 近さの測り方 | 文埋め込み／関係／ハイブリッド |
| 共通層 | 分野で共有する辞書（版がある） |
| 拡張層 | マップごとの追加の辞書（下書き→描き直すと版が上がる） |
| 部品（分野） | 共通層の中の分野ごとの塊。文書の分類で切り替える |
| 上層（共通の層） | どの分野の文書でも使う部品 |
| 概念・中間概念・別名 | 辞書の見出し語・まとまり・言い換え |
| 格上げ | マップの拡張層の語を共通層に入れること |
| 発行 | 共通層の下書きを版として固定すること |
| 用途の文／用途の段落 | 明細書から切り出した、用途を述べた文（確認用）／用途の段落（計算用） |
| 取りこぼし（率） | 段落の型の概念を 1 つも拾えない段落の割合 |

## 6. 作った側が気づいている課題（未対応）

1. 用語が多く、似た言葉が並ぶ（共通層・上層・共通の層・部品・分野・拡張層・下書き・版）。初見では関係が分かりにくい。
2. 地図の画面は 3 段組で、横 1440px でも地図の幅が 500〜700px 程度。左右の欄が縦に長く、スクロールが多い。
3. 右の欄の情報量が多い（書誌・5 つの折りたたみ・3 つのタブ・近い理由）。何から見ればよいかの順が弱い。
4. 「近い理由」は関係の対の羅列で、なぜ近いのかの要約（一言の説明）が無い。
5. 辞書の画面（マップの拡張層・共通層）が 2 系統あり、似た操作（候補を採用・別名・無視）が別の画面に分かれている。
6. 概念の修正が標準の入力ダイアログ（prompt）で、取り消し（元に戻す）が無い。削除や発行の確認も標準のダイアログ。
7. 候補の置き場所の提案は、名前の文埋め込みの近さで作るため当たりが悪い（例: 光触媒→太陽電池の別名）。画面ではそれを強く注意していない。
8. 計算の待ち時間（数百件で数分）の間、何が起きているかは段階の文だけ。残り時間の目安が無い。
9. 地図の色分けは最大 3 群。部品や用途が多いと足りない。
10. 空の状態・失敗の表示が画面によってまちまち（文だけ／赤字／標準のダイアログ）。
11. キーボード操作と読み上げへの配慮は最小限（タブの役割属性・ラベルはあるが、地図の点は操作できない）。
12. 共通層をつくるとき、AI の下書きのままだと取りこぼしが多い（試しで用途の段落の 6〜7 割）。「文書から足す」への誘導はあるが、ステップの外に出てしまう。
